Registered `ColumnReorderSuggestionSupport`, `TableConstraintChangeSuggestionSupport`, `TableIndexChangeSuggestionSupport` and `PartitionSchemeChangeSuggestionSupport` on `SnowflakeDialect`. The column-reorder, index-change and partition-scheme answers return the explicit unsupported state (`operations=False`): Snowflake has no column-position clause, plain index DDL is hybrid-table-only and unmodelled, and partitioning is AUTOMATIC micro-partitioning with no addressable partition DDL (`CLUSTER BY` is clustering, not partitioning). The table-constraint answer builds real single-action `ALTER TABLE` chains from the frozen point's live declarations: a PRIMARY KEY / UNIQUE / FOREIGN KEY drop is spelled by kind (`DROP PRIMARY KEY`, `DROP UNIQUE (cols)`, `DROP FOREIGN KEY (cols)`), a same-name redefinition is drop-then-add, and a named CHECK is removed by name. It still answers `False` where the grammar or the nodes cannot express the step -- an unnamed CHECK removal, any CHECK addition (which needs `ENABLE NOVALIDATE`), and constraints carrying enforcement, deferral or `NOT VALID`, which this dialect declines to render. The chains never contain `DROP TABLE` or `DROP SCHEMA`.

Answer core's neutral object-state API where Snowflake's catalogue can: `get_table_state()` reads one `INFORMATION_SCHEMA.TABLES` row for the table kind (`regular`/`transient`/`temporary`), clustering traits, comment and raw catalogue spelling (a missing table or a view raises `ObjectNotFoundError`); `get_partition_state()` answers `PartitionState(scheme=None)` -- Snowflake's micro-partitions are not user-addressable, so there is no scheme to report and no fabricated bound list -- while `include_stats` queries nothing; `list_sequence_states()` projects the existing `SEQUENCES` read onto `SequenceState` (`owned_by` stays `None` because the catalogue's owner is a role); `item_exists()` answers `SCHEMA`, `TABLE` (views excluded), `SEQUENCE` and `FUNCTION` with one filtered `LIMIT 1` read; and `list_schemas()` now returns the neutral `List[str]` while the complete schema records moved to the new `list_schema_infos()` (the CLI's `schemas` type uses the latter). The CLI gains no `partitions` type: a listing would print an empty table and call it an answer.
